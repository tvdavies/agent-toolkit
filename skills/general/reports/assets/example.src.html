Summary

The migration itself is sound. Latency doubled because replicas start cold and the warm-up job targets the old cluster. Point warm-up at the new cluster and raise the cache size, and p90 should return to about 210 ms.

  1. p90 latency rose from 205 ms to 430 ms on 12 August and has stayed there. p50 moved much less (88 → 104 ms), so the regression is in the tail.
  2. 83% of slow queries hit a replica that restarted in the previous hour. Warm replicas on the new cluster are as fast as the old ones.
  3. The nightly warm-up job still targets the old cluster. It has run successfully every night, against hosts that no longer serve traffic.

What changed on 12 August

Latency was flat through July. It stepped up on the day of the cutover and has not recovered.

Options considered

Roll back

Restores latency immediately but loses the index format gains and blocks the next migration.

Fix warm-up and cache size

Two configuration changes. Keeps the migration. Recommended.

Pin traffic away from new replicas

Masks the problem and halves effective capacity during deploys.

Recommendations

  1. Point the warm-up job at the new clusterP0Search platformEffort: S

    Update the job's target list and run it on replica start, not only nightly.

  2. Raise the replica cache from 4 GB to 8 GBP1InfraEffort: S

    The new index is 1.7× larger; the cache was not resized with it.

  3. Alert on p90 above the SLO for 30 minutesP2Search platformEffort: S

    The regression ran for 16 days before anyone looked.
